Mirage: a virtual terminal for AI agents

27 November 2026 · 4 min read

I'm studying Mirage, an open-source project from strukto-ai (Apache-2.0, marked experimental). The idea is simple to say and interesting to unpack: the terminal an AI agent uses should not be tied to one machine. Mirage separates the shell from the data and from the machines that run the work.

The problem it is solving

Language models are trained a lot on terminal sessions, so agents feel most at home in a shell. But a normal shell is bound to one computer and its kernel, with its files and its compute on that same machine. If the data lives in S3, Slack or Google Drive, the agent has to copy it locally first.

What Mirage does

A Mirage workspace mounts several services as folders, so one command can reach all of them:

  • Virtual filesystems. S3, Slack and Gmail appear as paths such as /s3, /slack and /gmail.
  • Virtual CLIs. A tool such as a Slack CLI is installed in the terminal and listed by which and man like any other program.
  • Machines. Python can run in-process on a small runtime, or on a remote sandbox. A route policy decides which line goes where.
  • Profiles. Each agent gets only the paths and commands its profile allows, such as hiding a secrets folder or denying a send command.

The example that made it click

The README sets up one workspace with three mounts, an "analyst" profile and two machines. The setup is code, and what the agent sees is ordinary shell output:

$ grep -rlw invoice /s3 /slack /gmail
/s3/billing/2026-10.csv
/gmail/INBOX/2026-10-21/Invoice_1042__18f3a9c2b7d1e0f4.gmail.json
$ cat /s3/secrets/aws.txt
cat: /s3/secrets/aws.txt: No such file or directory
$ slack send-message --channel general --text "report is up"
slack: Permission denied

One grep sweeps three services. The hidden folder does not exist for this agent, and the write is refused by policy. The agent is not told to behave. The environment is shaped so it cannot do the wrong thing.

Why it is lightweight

Each virtual terminal starts with only kilobytes of memory, and every layer is async down to each service call, so one process can serve many agents. The README lists places it can run: a Python or TypeScript server, a browser tab, a Cloudflare Worker and a Raspberry Pi. State sits on infrastructure that already exists, such as RAM, disk, Redis or S3, and every command can be exported as an OpenTelemetry trace.

What I took from it

  • Separate the interface from the storage. If the agent only sees paths and commands, the storage behind them can change without the agent noticing.
  • Permissions belong in the environment. A profile that hides a path is stronger than a line in a prompt saying "don't look there".
  • Record everything. A trace of each command is what makes an agent's work checkable after the fact.

I'm still reading the docs and have not run it in a project of my own yet. Next I want to build a tiny workspace with one mount and one profile, to see where the abstraction leaks.
